上周三早上发的一篇文章，阅读 4200、点赞 11；同一天晚上发的另一篇，阅读 1800、点赞 46。后者排进了掘金文章榜前 20，前者连影子都没见到。我盯了半天这两个数字，意识到自己过去半年一直在优化一件可能搞错方向的事：**把阅读量当成目标**。

于是我花了两天，把掘金官方榜单接口扒了一遍，拿 50 篇 3 日文章榜、30 篇 3 月收藏榜、7 个分类榜各 20 条做对照，逐篇拉详情、正文、发布时间和互动数据，再用最小二乘拟合了一次热度分。结论比我想的直接得多，也把我之前几条「经验」直接推翻了。

本文原创首发，所有数字来自 2026-11-06 08:55（UTC+8）的一次完整快照，抓取与统计脚本都放在文末仓库里，可以自己跑一遍复现。

## 1. 先搞清楚「热榜」到底是哪张榜

掘金页面上看到的推荐流，和官方榜单接口返回的并不是同一批内容。我一开始用页面渲染结果做统计，做到一半发现对不上：页面里有大量高阅读的文章，压根不在 3 日榜里。

这个坑值得单独拎出来说。**推荐流是个性化分发，文章榜是有窗口的排序结果**，两者口径完全不同。想研究「怎么上榜」，就必须打到榜单接口本身，而不是抓页面。

我从前端打包文件里翻出了调用方式：`GetArticleRank` 接受 `category_id` 与 `type` 两个参数，`type=hot` 对应文章榜，`type=collect` 对应收藏榜。页面上也写明了口径：文章榜取最近 3 天发布的文章，收藏榜取最近 3 个月发布的文章。

> 一句话：不先确认口径，后面所有统计都是在给错误的对象画像。

## 2. 抓数据的两个硬门槛

榜单接口本身是 GET，参数很简单。真正卡住我的是文章详情：一开始只传 `article_id`，接口直接回「参数错误」，换成 GET 又回「请求路由不存在」。把请求体里补上两个数字型字段才通。

```python
API = "https://api.juejin.cn/content_api/v1"

def fetch_rank(rank_type="hot", category_id="1"):
    url = f"{API}/content/article_rank?category_id={category_id}&type={rank_type}"
    return request_json(url)["data"]

def fetch_detail(article_id):
    # aid 与 client_type 必须是数字，写成字符串会返回「参数错误」
    return request_json(f"{API}/article/detail", {
        "article_id": str(article_id),
        "aid": 2608,
        "client_type": 2608,
    })
```

整个抓取链只用 Python 3.13 的标准库（`urllib.request`、`json`、`csv`），在 Windows 和 macOS 上都能直接跑，不需要装任何第三方包。我一共落了 80 篇文章的详情：标题、正文 Markdown、发布时间、分类、标签、封面、字数、阅读、点赞、评论、收藏，逐篇存成 JSON 再合并成特征表。

这里有个细节：详情里的 `mark_content` 是完整正文，我靠它统计章节数、代码块数、图片数和字数；`content_count` 是平台给的字数，两者交叉验证过，差异在可接受范围内。

## 3. 热度分其实是一个很朴素的公式

把 50 篇文章的四个互动指标和发布时间丢进最小二乘，出来的系数是：阅读 0.4488、点赞 8.3955、评论 9.1051、收藏 0.2265。收藏的系数几乎贴着 0，而点赞和评论的系数约是阅读的 20 倍。

我又往回验了一遍离散形式：

```
hot_index = 9 × round( 阅读 / 20 + 点赞 + 评论 )
```

50 篇文章的热度分**全部能被 9 整除**，其中 48 篇按这个式子算出来误差不超过 1 分。剩下的误差来自抓取时刻与榜单计算时刻之间新增的互动。

| 指标 | 折算成热度分 | 说明 |
|---|---|---|
| 20 次阅读 | 1 分 | 权重最低 |
| 1 个点赞 | 1 分 | 与评论等价 |
| 1 条评论 | 1 分 | 评论略高于点赞 |
| 1 个收藏 | ≈ 0 分 | 文章榜不计，收藏榜才计 |

**所以 1 个赞 ≈ 1 条评论 ≈ 20 次阅读。** 这一条直接解释了开头那两篇文章的反差：4200 阅读折 210 分，加 11 个赞也就 221 分；1800 阅读折 90 分，46 个赞就有 136 分——看着差一半的阅读，实际热度权重并不在同一个量级上，再加上评论区差异，排名反过来完全说得通。

## 4. 收藏是另一条赛道，别混着优化

30 篇收藏榜样本和 3 日榜的画像几乎是两种内容。收藏榜是 3 个月窗口，考的是「值不值得存下来」：清单、速查表、成体系的教程、可复用的配置模板占了大头；3 日榜则明显偏向热点绑定、发布快、信息密度高的实战复盘。

具体到标题，差别很直观：3 日榜 38% 用「术语：副标题」的冒号结构，收藏榜只有 13.3%；长尾高价值样本的标题中位数 23 字，比 3 日榜的 32 字短了近 1/3。

我的做法是不二选一，而是**双目标**：主攻 3 日榜的选题和热词，同时把正文写成值得收藏的产物。这样三天内吃到互动权重，三个月里还能靠收藏慢慢涨。

> 如果你的目标是账号长期沉淀，就别盯着 3 日窗口卷发布时间了，那 3 天一过热度清零，什么也留不下。

## 5. 能直接抄走的发布配置

把统计结果翻译成发布动作，是一张很短的清单：

- **时段**：优先工作日 08:00–10:00，50 篇样本里 48% 落在这个窗口；次选 20:00–21:00。拍脑袋选的「午休发」在样本里几乎没出现。
- **标签**：恰好 3 个 = 1 个大分类 + 1 个技术栈 + 1 个热点词。别堆 5 个热词，标题里出现超过 1 个热词反而稀释信息。
- **分类**：看分类榜门槛表，选竞争度低的入口，同样的内容在不同分类的难度不一样。
- **封面**：约 62% 上榜文章有封面，配一张和标题强相关的图。
- **冷启动**：3 天窗口里，发布后 24–72 小时是唯一冲榜期。首日在评论区补一条延伸问题或勘误，认真回前 10 条评论。
- **引导方向**：明写「觉得有用点个赞 / 有不同做法评论区聊」，而不是只求收藏——收藏对文章榜没用。

最后一条最容易被忽略。我以前结尾一律写「建议收藏」，等于把读者最值钱的一次互动引导到了不计分的动作上。

## 6. 标题和正文，哪些真的影响了互动

我算了一个自己更看重的指标：每千阅读互动数 `(点赞 + 收藏 + 评论) / 阅读 × 1000`。3 日榜中位约 20.7，长尾高价值样本约 34.2。它比绝对阅读量更能说明内容是否真的对上了读者。

按这个指标筛掉一批「高阅读零互动」的异常样本后，剩下的文章共性很清楚：

- 标题 18–28 字、含具体数字或具体对象，比如「8 个坑」「72 小时」「22 个前端」。
- 正文 2500–3500 字、5–8 个编号章节，每节 300–500 字，长文带目录。
- 至少 1 段可运行代码、1 张表格或图、1 组真实数据。
- 开头用结论先行、具体事故现场或提问，不铺概念；结尾有总结、一个具体提问和资源链接。
- 有失败记录和边界说明。样本里那些只讲成功、不给适用条件的文章，互动率明显偏低。

**结构性差异里最稳定的一条是「可带走的产物」**：读者能复制一段代码、一条命令或一张对照表，才愿意点赞。纯观点文即使阅读不错，互动也普遍偏薄。

## 7. 这套结论的局限，得说在前面

第一，这是**单次快照**，样本只有 50 + 30 篇，平台算法随时可能调权重，别把它当成官方披露的规则。拟合出来的系数是经验结果，不是接口文档。

第二，热度分只解释了「排序怎么算」，没解决「什么内容会被推荐」——曝光入口在更上游，这份数据看不到。阅读量本身仍受分发影响，我只研究互动权重，不研究流量分配。

第三，相关性不等于因果。48% 上榜文章早上发，不代表「改成早上发就能上榜」，更可能是活跃作者本来就在早上发。这一条我目前**没解决**，只能作为弱建议。

第四，样本里存在高阅读零互动的异常数据，我用「每千阅读互动 < 5」过滤掉了 3 篇；换一个阈值，个别百分比会变。所有中间数据和过滤逻辑都在仓库的 `analysis/` 产出里，可以自己重算。

所以这份结论的正确用法是：**当作发稿前的检查表，而不是爆款保证书。**

## 小结

把 50 篇文章拆完，我改动最大的是三件事：结尾从「建议收藏」改成「有不同做法评论区聊」、发布时间固定在早上 8 点半、每篇文章必须留一段可复制的代码或清单。热度公式给了一个很朴素的判断标准——**与其追 20 次泛泛的阅读，不如认真让 1 个读者愿意点个赞**。

你最近一次发文是踩中了早高峰还是随手在深夜发的，有没有对照过点赞和阅读的比值，算出来每千阅读互动是多少呢？欢迎把数字贴在评论区，我想看看不同分类的差距有多大。

完整配置、抓取脚本、80 篇逐篇特征表和可直接复制的发布清单都在 github.com/ijry/juejin-hot-article，仓库里的 `score_article.py` 可以给草稿打 100 分并列出优先改进项，发稿前跑一次比凭感觉改有用得多。
