# 文章骨架与写作规范

样本基线：3 日榜中位 2500 字 / 收藏榜中位 3271 字；56%（收藏榜 66.7%）有编号章节；50% 提问开场、42% 背景铺垫、36% 结尾互动引导、22% 附资源链接、62% 有封面。以下骨架把这些「多数派做法」补齐并补上多数文章缺的部分（真实数据、失败记录、明确互动设计）。

## 通用规格（默认，不达标需在交付时说明原因）

| 项 | 目标 |
|---|---|
| 正文字数 | 2500–3500 字（深度原理可到 5000，清单类可 1500 + 长附录） |
| 章节 | 5–8 个编号二级标题，每节 300–500 字，长文加目录 |
| 证据 | ≥1 段可运行代码/命令、≥1 张图或表格、≥1 组真实数据、≥1 处失败或边界说明 |
| 开头 | 前 150 字内出现结论/事故现场/代价，禁止先讲行业背景 |
| 结尾 | 总结 + 一个具体提问 + 资源链接（仓库/文档/配置） |
| 节奏 | 每 2–3 段出现一个可扫读元素：小标题、代码块、表格、加粗结论、引用块 |

## 骨架 A：实战复盘（默认首选）

适合：我用 X 做了 Y、上线了一个项目、从 0 到 1 的过程。

```
# {标题：第一人称 + 具体产物 + 数字}

> 一句话结论：{做完后的真实结果 + 关键数字}。{代价/边界是什么}。

## 1. 为什么要做这个（≤200 字）
具体触发场景：什么时间、什么任务、原来的做法卡在哪。不写行业趋势。

## 2. 最终效果：先给结果
截图 / 数据对比表 / 可访问链接。列出 3 个关键指标（耗时、体积、成功率…）。

## 3. 技术选型：我试过哪几条路
| 方案 | 为什么选/不选 | 实测结果 |
把淘汰理由写清楚，这是最容易被收藏的部分。

## 4. 核心实现（含可运行代码）
按「关键决策 → 代码 → 为什么这么写」组织，代码标注语言、版本、运行环境。

## 5. 踩过的 N 个坑
每坑：现象 → 复现条件 → 根因 → 修复 → 可复用检查项。

## 6. 边界与没解决的问题
明确哪些场景不适用、还有哪些没验证。这一段是可信度的主要来源。

## 7. 小结 + 可带走清单
3–5 条要点，附仓库/配置/命令清单。
最后一句：一个具体、可回答的提问（例如「你们在 X 场景下是怎么处理 Y 的？」）。
```

## 骨架 B：踩坑排错

适合：报错、性能问题、兼容性、线上事故。

```
# {标题：现象 + 反常识原因 / N 个坑}

> 结论先行：问题是 {根因}，改 {一处} 后 {指标} 从 A 变 B。

## 1. 事故现场（时间、环境、版本、报错原文）
## 2. 先排除掉的 3 个「看起来很像」的原因（附验证命令）
## 3. 真正的原因（原理图 / 调用链 / 最小复现）
## 4. 修复方案与可运行代码
## 5. 修复前后对照（表格 + 真实数据）
## 6. 怎么避免再犯：检查清单 5 条
## 7. 小结 + 提问（你遇到过 X 的哪种变体？）
```

## 骨架 C：清单测评〔最利于收藏榜〕

适合：N 个工具/插件/配置项/面试题。

```
# {标题：N 个 X，我全试了，只有 M 个能用}

> 评测口径：环境/版本、样本、评分维度、淘汰标准（写清楚才可信）。

## 1. 结论速查表（一张表列出全部候选项 + 推荐度 + 适用场景）  ← 收藏钩子前置
## 2. 评测方法
## 3. 推荐的 M 个：逐个给「装法 + 实测截图 + 一个真实用法」
## 4. 淘汰的 N−M 个：逐个给一句淘汰理由
## 5. 组合用法 / 配置模板（可直接复制）
## 6. 注意事项与版本坑
## 7. 小结 + 提问（你还有哪个在用？）
```

## 骨架 D：原理深挖

适合：源码、协议、算法、框架机制。

```
# {标题：反常识疑问 或 具体数字对比}

> 先抛出反直觉结论，再说明它成立的条件。

## 1. 一个能跑起来的最小例子
## 2. 现象与预期不符在哪
## 3. 逐层拆解（配调用链图 / 时序图 / 源码位置）
## 4. 用数据验证推断（benchmark 或日志，注明环境）
## 5. 工程上怎么用 / 不该怎么用
## 6. 边界与常见误解
## 7. 小结 + 参考链接 + 提问
```

## 骨架 E：观点争议〔最利于评论〕

适合：行业变化、职业、技术选型之争。

```
# {标题：X 是 A 还是 B？/ 为什么 X 之后 Y 没变？}

> 直接给立场，不铺垫。

## 1. 我见到的具体事实（时间、团队、数据，不用「据说」）
## 2. 反方最有道理的那条论据（先认真复述）
## 3. 我不同意的原因（数据或经历）
## 4. 一个被忽略的约束条件
## 5. 对不同人群分别给建议（表格）
## 6. 我可能错在哪
## 7. 小结 + 明确提问（欢迎用具体经历反驳）
```

## 开头句库（选一种，禁止套话）

- 结论型：「先说结论：改成 X 之后，构建从 4 分 12 秒降到 38 秒，但只在我们这种单体仓库成立。」
- 事故型：「上周三下午，线上 30% 的请求开始返回 502，日志里只有一行 `connection reset`。」
- 提问型：「为什么 8 个大核的手机，Raster 线程只跑在 2 个核上？」
- 反常识型：「被吹了三年的 X，我们压测下来反而是最慢的那个。」
- 数据型：「我把 22 场面试的记录翻了一遍，出现频率最高的不是算法题，是 X。」
- 代价型：「这套方案能省掉 80% 的 API 费用，代价是首次响应慢 300ms。」

**禁用开头**：「随着人工智能的快速发展…」「在当今前端领域…」「众所周知…」「本文将带你深入了解…」。

## 结尾句库

- 总结 + 边界：「以上结论只在 {环境/版本} 下验证过；{场景} 我没有测，别直接照搬。」
- 具体提问：「你们在 {具体场景} 是怎么处理 {具体问题} 的？贴一下配置我对比看看。」（比「欢迎留言讨论」有效得多）
- 资源：「完整配置/仓库/复现脚本在 {链接}，可直接跑。」
- 收藏钩子：「第 3 节那张速查表建议存一份，下次选型直接用。」

## 去 AI 味对照

| 套话 | 替换 |
|---|---|
| 随着技术的不断发展 | 写具体时间/版本/事件 |
| 综上所述，本文介绍了 | 直接给 3 条结论 |
| 首先…其次…最后… | 用编号小标题 + 每节第一句给结论 |
| 极大地提升了性能 | 从 A 降到 B（附测试环境） |
| 需要注意的是 | 直接写约束条件与后果 |
| 有很多方案可供选择 | 列出你试过的 3 个和淘汰理由 |
| 希望能帮助到大家 | 删掉，换成一句具体提问 |

## 每节自检

1. 这一节读者能带走什么？（结论 / 代码 / 配置 / 表格 / 检查项）
2. 有没有具体数字、版本、环境？
3. 有没有说明失败、边界或代价？
4. 段落是否超过 5 行？超过就拆或加代码块。
5. 标题承诺的内容，能在哪一节兑现？
